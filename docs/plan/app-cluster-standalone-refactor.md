# App-cluster migration to standalone PVE

## Scope and ownership

-   Replace only the Proxmox-hosted **app-cluster** with a fresh Talos/Kubernetes cluster: `k8s-ctrl-01` (`10.0.40.90`, VM 4090), `k8s-wrkr-01-gpu` (`10.0.40.95`, VM 4095), `k8s-wrkr-02` (`10.0.40.96`, VM 4096), `k8s-wrkr-03` (`10.0.40.97`, VM 4097). The API VIP remains `10.0.40.101` pending validation. The controller hosts control-plane components, not user workloads.
-   The **two physical infra-cluster nodes are unchanged**. Do not change their Talos, workloads or kubeconfig as part of this migration. Their Argo Applications remain managed by the app-cluster Argo hub.
-   `../home-dc-proxmox` configures the standalone `pve-00` host; `../home-dc-terraform` provisions new guests with independent state. This repository owns Talos and Kubernetes, not the old Proxmox root. The old and new OpenTofu states are **not** automatically transferable. Preserve a recoverable, private copy of the old state until resource ownership is independently reconciled; never run the old root's apply or destroy to perform this cutover.

## Storage decision and prerequisite

There is **no Ceph cluster**. CephFS-backed PVCs cannot be mounted in the replacement cluster; do not carry their StorageClass, CSI credentials or provisioner into the new deployment. Keep the existing NAS NFS media claim (`10.0.40.2:/media`) for media/downloads. For app config and databases, use node-local volumes with off-node backups and restore checks. This avoids putting every small database operation on the 1 Gb NAS link. Node-local volumes do not survive worker disk/host failure and cannot move with a pod; recovery requires a backup and restore.

Current worker VMs have only a 55 GB system disk each, all on the **same physical `local-hdd` pool**. Do not create replicated Longhorn volumes across them: three replicas would share a single HDD and host failure domain. Before using Talos user volumes for the local-path provisioner, add dedicated worker data disks in the Proxmox Terraform repository, size against the PVC inventory and reserve headroom for databases and restores; prefer independent NVMe capacity for latency-sensitive state if available. Do not use the Talos system/EPHEMERAL volume as an unexamined substitute. Confirm Talos sees the additional disks and mounts the user volumes, then install the local-path provisioner, restrict it to workers, use `WaitForFirstConsumer` and `Retain`, and use `ReadWriteOnce` for per-pod claims. Tdarr is retired rather than attempting to share one local claim among its controllers. The NAS and PVE host still require separate backups; VM or local-volume snapshots alone do not protect against host loss.

Each worker now has a dedicated 100 GiB guest data disk and a 90 GiB Talos `local-path-provisioner` user volume (about 97 GB usable partition size as reported by Talos). After retiring unused apps, surviving manifest PVC requests total 25 GiB on the GPU worker (Jellyfin config/cache), 22 GiB on worker 02 (Immich database/Redis), and 23 GiB on worker 03 (Immich machine-learning cache and media managers). These are **requests, not enforced local-path quotas**: measure actual bytes, filesystem headroom and restore growth before deploying. The single `local-hdd` pool remains a shared host failure domain.

## Security and failure domains

The `local-path-storage` helper namespace and `gpu-operator` namespace require privileged pods to manage host storage and NVIDIA devices. Keep their Argo Applications scoped to the app cluster, review their chart versions and restrict access to the Talos and Proxmox APIs. The sole PVE host and its `local-hdd` pool are shared failure domains; Retain prevents automatic deletion, **not** data loss. Store encrypted, application-consistent backups off-host and verify restoration before migrating databases. Keep the old OpenTofu state and kubeconfigs private. The NAS remains a separate network dependency for media and backup restores; do not expose its export to untrusted networks.

## Stateful application cutover decisions

-   Jellyfin, Immich and the media-management apps (Radarr, Sonarr, Prowlarr, qBittorrent, SABnzbd, Jellyseerr, Recyclarr): deliberately start with new application state; existing NAS media files are retained. Do not delete any old backup as part of this choice.
-   Home Assistant, Linkwarden, Code Server, Sterling PDF, Glance, nginx-test and the entire app-cluster Grafana/Prometheus stack are retired. Homepage stays. Remove only their app-cluster GitOps resources and their obsolete DNS/Access entries; regenerate the infra-cluster AutoKuma inventory to withdraw monitors for these retired app-cluster routes without changing physical infra nodes or their own services. The `ha.krapulax.home` record was dynamically managed from its HTTPRoute, not Terraform.
-   The other small app state starts fresh. Doppler manages secrets, not PVC contents; verify scoped Doppler tokens and encrypted bootstrap references before creating GitOps Applications. The remote GitOps `main` branch must contain this refactor before syncing the root Argo Application; otherwise it will deploy old Ceph and retired apps.

### Public exposure gate

Cloudflare already has public DNS records for the app-cluster HTTPRoute hosts. The initial webhook-only tunnel kept stateful apps inaccessible until backups and restore checks; the operator explicitly chose to reopen public apps before that gate on 2026-10-29. This accepts potential permanent loss of fresh PVC state if a worker or `pve-00` fails before off-host recovery is in place. Preserve the exact path-scoped Argo webhook bypass first, then the prior apex and wildcard routes to the TLS-verified external Envoy Gateway (`originServerName: external.krapulax.dev`), then fallback 404. Keep `cloudflare-dns` manual: existing records already resolve through Cloudflare, and enabling external-dns now risks publishing private Envoy IPs. The physical infra tunnel is unchanged.

Validate the live ingress order and origin TLS, Argo UI/Homepage/media routes, external webhook handling, and the physical infra tunnel. Cloudflare Access challenges can precede origin checks; test private Envoy routes separately and have an authenticated user test protected public pages. Confirm public DNS resolves existing hosts to Cloudflare rather than private IPs. Do not declare stateful apps recoverable until off-host backups and a restore test are complete. If exposed routes fail or create an unsafe origin path, revert this Git revision to webhook-only ingress; `cloudflare-dns` stays manual, and the operator must be told that public apps will be unavailable again. A healthy tunnel pod alone is not proof.

## Execution gates (stop on failure)

1. **Inventory and recovery:** Record VMIDs and ownership in both OpenTofu states and on `pve-00`; confirm no VMID collision or accidental replacement. Inventory existing app PVC data and decide restore versus deliberate fresh start per application; retain old encrypted secrets, PVs and offline state securely until validated. Record DNS, ingress and external-dns targets. Never commit kubeconfigs or backup contents.
2. **Storage:** Provision dedicated data disks and Talos user volumes on each worker; confirm mount status, free capacity, local-path PVC binding and a write/read/restart smoke test. Confirm NAS NFS mounts from each worker. Any app chosen for restoration must have its data staged and checked for ownership and database consistency before its first application sync. For deliberately fresh apps, initialize new state, then take and verify an off-node backup **before public DNS cutover**. No Ceph CSI deployment in the fresh cluster.
3. **Talos bootstrap:** Verify VLAN 40 networking, primary NIC MACs and disk names from the new VM inventory; the Ceph-only VLAN 70 NIC has been removed. Generate configuration for one controller and three workers using the existing API VIP; bootstrap etcd **once** on the controller. Verify endpoint, `talosctl health`, four `Ready` nodes, Cilium and CoreDNS. Do not run old three-controller removal procedures on this fresh cluster.
4. **GitOps and placement:** Install Cilium with `task bootstrap:network`, then install foundational charts with `task bootstrap:platform`, including the declarative `app-cluster` Argo destination. Reconnect only the existing physical `infra-cluster` destination with `task clusters:register-infra` (approved limited ServiceAccount/RBAC registration). Merge the reviewed refactor to remote `main` before running `task apps:bootstrap`; otherwise GitOps deploys old Ceph and retired apps. Verify worker placement, local-path and NFS claims, pod readiness, Service endpoints and actual routes. The controller remains tainted.
5. **GPU:** Confirm P2000 graphics/audio passthrough and NVIDIA's proprietary-driver license acceptance. The P2000 (`10de:1c30`) requires the Talos v1.13.8 **580-series LTS** `nonfree-kmod-nvidia-lts` and `nvidia-container-toolkit-lts` extension pair, schematic `af8eb82417d3deaa94d2ef19c3b590b0dac1b2549d0b9b35b3da2bc325de75f7`; the old 595-series production schematic does **not** support it. Ensure the GPU worker boots the LTS image and modules load before the GPU operator/device plugin starts. Require advertised `nvidia.com/gpu` before scheduling Jellyfin there. Verify playback and an actual hardware transcode, not merely pod readiness; retain a documented CPU-transcode rollback.

    NVIDIA chart v26.3.1 must render `ClusterPolicy.spec.operator` as an object; setting `operator.runtimeClass: ""` renders it as `null` and the API rejects the policy. Leave the chart's default `operator.runtimeClass: nvidia` for GPU operand pods; the rendered GPU operator Deployment itself has no `runtimeClassName` and remains schedulable on a general worker. Validate the rendered ClusterPolicy and live GPU resource before relying on Jellyfin scheduling.

6. **Internal DNS:** The `k8s-gateway` image `quay.io/oriedge/k8s_gateway:v0.4.0` now returns registry 401 on anonymous pulls. Migrate the app-cluster DNS service to the maintained first-party k8s-gateway chart 4.0.1 and its public Codeberg image 1.9.2; pin the verified image digest, retain the `10.0.40.153` private LoadBalancer and `krapulax.dev` Service/HTTPRoute records with TTL 1, and render-check the new Corefile/RBAC/Service before merging. The old SOPS values contain no encrypted data (only a MAC), so replace them with ordinary chart values instead of keeping dead encrypted-chart wiring. Verify internal DNS queries and Service readiness after GitOps sync, without changing Technitium's separate `krapulax.home` authority or enabling public DNS. If the replacement fails, keep the public DNS gate closed and temporarily serve required private records from Technitium while repairing the chart; the inaccessible Quay image is not a viable rollback.

7. **Public exposure and recovery:** The operator accepted early public exposure without an off-host restore path. Preserve the manual `cloudflare-dns` sync gate, verify Argo, Homepage, Jellyfin `/health`, ready Service endpoints, media playback, external routes, and application authentication. Take off-host backups of all fresh stateful PVCs and prove a restore as the next recovery priority. Never delete old backups or retained PVs as an implicit cleanup step.

## Rollback

Before DNS cutover, stop sync to the replacement app cluster and keep the old cluster/routes available if still operational. After cutover, revert DNS/ingress to the old deployment **only if its storage and data remain usable**; otherwise restore the last consistent backups onto the new local volumes and reapply the previous Git revision. Roll back a failed Jellyfin GPU path by removing the GPU requirement and using CPU transcode on a worker with a suitable RWO volume; do not reschedule a node-local PVC onto another worker without restoring its contents. A single `pve-00` failure requires host recovery plus off-host backup restores, not Kubernetes replica failover.

## Validation

-   Read-only: compare PVE VMID list with both OpenTofu state inventories; inspect Talos disk and NVIDIA extension/device inventory without printing secrets.
-   Render Talos and Argo/Kustomize manifests; verify exactly one controller, three workers, no Ceph CSI apps/StorageClass and no old controller placement pins.
-   On the replacement cluster only: `kubectl --kubeconfig kubeconfig get nodes -o wide`, PVC/PV binding and node affinity, storage write/read/restart probe, pod readiness, ready endpoints, application HTTP and GPU transcode checks.
-   On the physical infra cluster: read-only health check using `.private/infra-cluster/kubeconfig`; no configuration changes.
