# VictoriaMetrics monitoring

**Decision date:** 2026-11-01. **Status:** proposed for GitOps deployment; the Kubernetes stack is not yet deployed or accepted as a complete Pulse replacement. Pulse was retired in PR #460. The planned end-to-end coverage and acceptance criteria are in [the monitoring plan](../plan/victoriametrics-monitoring.md); complete the post-deployment checks and explicitly resolve the gaps below before relying on the stack.

## Scope and security

The infra-cluster hosts the VictoriaMetrics operator and single-node metrics store, vmagent, vmalert, Alertmanager and Grafana. Grafana is exposed only through the internal `grafana.krapulax.home` HTTPRoute. This HTTP endpoint assumes the home network is trusted; Grafana requires authentication and public exposure is not configured. Its admin user and password are stored in `home-dc-kubernetes/infra` in Doppler as `GRAFANA_ADMIN_USER` and `GRAFANA_ADMIN_PASSWORD`. Alertmanager syncs only `SLACK_WEBHOOK_MONITORING` into its own namespace-scoped Secret, mounts it as a file and sends resolved notifications. An isolated Alertmanager using the production receiver delivered one synthetic firing and one resolved notification to Slack without reported failures; the deployed stack still requires end-to-end validation.

The chart's Alertmanager component uses the short name `alerts`: its default generated StatefulSet name made the Kubernetes controller-revision label exceed 63 characters and prevented Pod creation. This override affects Alertmanager and its generated notifier/secret names only, not the VMSingle PVC. Validate the new StatefulSet, notifier target and a firing/resolved Slack test after reconciliation.

The PVE exporter is an independently reconciled app in infra-cluster. It uses the dedicated `prometheus@pve!victoriametrics` read-only, privilege-separated `PVEAuditor` token, maintained by the Ansible role in `home-dc-proxmox`. Doppler exposes the host project's `PVE_MONITORING_TOKEN_SECRET` to the infra config by cross-project reference; the operator's service identity was verified to resolve it. The token is mounted as a file, never baked into the chart or command line. The exporter validates `10.0.40.10:8006` against the independently acquired PVE CA. A certificate-authority replacement must be verified via a trusted host connection and updated in Git before it can be trusted by the exporter. See the host repository's `docs/monitoring-credentials.md` for token provisioning, expiry, rotation and revocation.

The separately reconciled PBS exporter uses `prometheus@pbs!victoriametrics`, an audit-only token provisioned by `home-dc-terraform`'s `pbs-monitoring-apply` task. Its token is referenced into `home-dc-kubernetes/infra` from Doppler and mounted as a file. PBS uses a self-signed certificate whose SAN contains `pbs.krapulax.home`, not its IP; the exporter pins the public certificate and maps that name to `10.0.40.20`. Verify a replacement certificate over trusted PVE access before updating the pinned public certificate in Git. The exporter was tested against PBS 4.2.8 with verified TLS. The certificate and ACLs must be rotated deliberately; see `home-dc-terraform/proxmox/README.md`.

For cross-cluster ingestion, the app-cluster vmagent sends remote-write traffic to an infra-cluster TLS proxy at `10.0.40.107:8443`. The proxy accepts only `POST /api/v1/write` from a client with a certificate signed by a dedicated monitoring CA; it forwards that path to VMSingle and exposes no query or admin API. The server certificate contains the load-balancer IP as a SAN. Server and client private keys are scoped to the infra and apps Doppler configs respectively; the public CA is shared. This is a private-LAN endpoint, not public ingress. An isolated test verified that authenticated writes succeed, unauthenticated requests and non-write paths fail, and queued samples survive an agent restart and are replayed. Cluster routing and actual alert delivery remain unverified.

PVE disk and pool collection supplements the upstream exporter using the same read-only token and TLS-verified PVE API. A separate unprivileged collector reads SMART and ZFS status without SSH or privileged Pods. SMART temperature and wear data depend on what the API reports for each disk. For board and CPU sensors unavailable through that API, `home-dc-proxmox` installs Debian's unprivileged node-exporter on `10.0.40.10:9100`, restricted to mutually authenticated TLS with a dedicated CA. Its server key is scoped to `home-dc-proxmox/prd`; the infra collector's client key is scoped to `home-dc-kubernetes/infra`. The CA private key is discarded. `task monitoring:pve-hardware-pki-check` checks the identities and `task monitoring:pve-hardware-pki-create` creates them only when all are absent. The host service is already applied; its Ansible role and procedures are in `home-dc-proxmox` PR #18, stacked on credential PR #17.

PBS task monitoring uses the audit-only `/nodes/localhost/tasks` API. A separate read-only collector reports the latest completed outcome per backup/verify/prune/GC/sync task identity, a scrape-success signal and whether the bounded task-history limit was reached. Running tasks and task messages are not exported; the latter may contain sensitive details. A newer successful completion clears a prior failure. Missing schedules and jobs that never run require separate inventory/freshness checks; a task listing alone cannot prove successful backups.

PVE currently schedules guests 4090 and 4095–4097 weekly on Sunday and PBS guest 4020 monthly. Freshness alerts use nine-day and 40-day thresholds respectively, including explicit alerts for missing guest series; update those thresholds and IDs when schedules or inventory change. At inspection, the latest snapshot verification metrics for all five guests were `0`, and PBS had no configured verify jobs. The exporter uses `0` for both unverified and failed verification, so a single delayed warning says “not verified OK”; inspect PBS rather than treating `0` alone as proof of failure. Configure and independently validate verification before relying on these backups.

## Coverage and deliberate gaps

-   Infra vmagent is configured to discover resources across namespaces, with `cluster=infra-cluster`. Kube-state-metrics and node-exporter provide initial node, workload and filesystem signals. Actual target health and Talos host mounts are not yet verified.
-   Node-exporter collects Talos `/var` and the app worker local-path user volume. A separate unprivileged filesystem-only exporter mounts `/media` and `/k8s-backup` read-only to expose NAS export capacity without granting host filesystem access. Isolated smoke tests scraped both local filesystems on an app worker and both NFS exports on the infra worker; production discovery and alerts must still be verified after deployment. A collector unable to mount or read an export reports telemetry unavailable, not proof of NAS failure.
-   App-protect CronJobs are checked for stale or never-successful config exports, using the current daily schedule. This does not prove that Backrest subsequently created, checked or restored a snapshot; Backrest plan freshness and restore verification remain separate monitoring gaps.
-   Kubelet, cAdvisor and resource scrapes are disabled because the node-serving certificates do not chain to the cluster CA. API-server proxying is not assumed to fix this. The existing app-cluster metrics-server still has its pre-existing `--kubelet-insecure-tls` setting; this deployment does not change that workload. Its insecure ServiceMonitor is disabled and excluded from conversion. Do not add insecure VictoriaMetrics scrapes; restore these metrics only after establishing verified serving identities.
-   PVE host, VM and storage metrics, disk SMART health and temperature, ZFS pool health, PBS availability, datastore capacity, snapshot timestamps and recent completed task outcomes were tested with isolated hardened collectors. The authenticated host exporter returned CPU, chassis fan and ZFS metrics; Kubernetes ingestion and complete scheduled-job coverage remain unverified.
-   The app-cluster collector converts existing Prometheus `ServiceMonitor` and `PodMonitor` resources, excluding the insecure metrics-server monitor. Its encrypted, mutually authenticated remote-write path and queue replay were tested in isolation, but it is not deployed. Real target coverage, converted monitors and cross-cluster routing remain unverified.
-   QNAP telemetry is optional and not implemented. Uptime Kuma continues to own external website checks.
-   No in-cluster firing/resolved Slack notification, dashboard, storage capacity, backup restore or end-to-end runtime validation has yet been completed. Pulse's monitoring gap remains open.

## Storage and recovery

VictoriaMetrics uses a 20 GiB `local-path` PVC with 30-day retention. Its metric history is intentionally opted out of app-protect and can be lost with the worker; a retained local PV is not an offsite backup. Grafana has no persistent database: provisioned dashboards, datasource settings and admin credentials are reconstructed from Git and Doppler. UI-created dashboards, user accounts and other unprovisioned changes will not survive a restart. Alertmanager silence persistence is not configured; active silences can be lost on restart.

The app vmagent uses a 5 GiB `local-path` PVC with a 4 GiB queue limit; its transient queue is explicitly opted out of app-protect. Oldest buffered metrics are dropped if the limit is reached. The volume is node-local and retained; if its worker is lost, restore is not available and buffered samples are lost. `task monitoring:remote-pki-check` checks existing Doppler identities and fails if they are incomplete or within 30 days of expiry; `task monitoring:remote-pki-create` creates them only if all are absent. The tasks require a Doppler identity able to access both the `infra` and `apps` configs. The one-year server and client certificates require planned coordinated replacement before expiry: generate and verify a new CA plus both identities, update both Doppler scopes, restart the proxy and collector, verify mTLS and queued replay, then retire the old credentials. The CA private key is discarded at initial creation, so this is a coordinated rotation, not an in-place certificate renewal. Do not rotate only one side.

## Validation and lifecycle

Render the chart with `helm template --include-crds`, render both kustomizations, and validate custom resources against the rendered CRD schemas. The chart's mutable dashboard/rule download job and Helm pre-delete cleanup hook are disabled; CRDs require an explicit reviewed lifecycle and must not be removed while other VictoriaMetrics resources use them. Validate rules with `promtool` and Alertmanager config with `amtool`. After deployment verify all scrape targets and labels, the internal Grafana route, correct dashboard data, firing and resolved Slack delivery, resource use and retention. Exercise recovery without disrupting Backrest.

Rollback is to revert the relevant Argo Applications and manifests, preserving PVCs, Doppler secrets and shared CRDs until their ownership is reviewed. Do not delete the monitoring namespace or Uptime Kuma. A complete infra-cluster, NAS or power outage can also take down this monitoring stack; an independent external dead-man alert remains separate work.
