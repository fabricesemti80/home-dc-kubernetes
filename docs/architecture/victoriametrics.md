# VictoriaMetrics monitoring

**Decision date:** 2026-11-01. **Status:** partially deployed; not yet accepted as a complete Pulse replacement. Pulse was retired in PR #460. The planned end-to-end coverage and acceptance criteria are in [the monitoring plan](../plan/victoriametrics-monitoring.md); complete the post-deployment checks and explicitly resolve the gaps below before relying on the stack.

## Scope and security

The infra-cluster hosts the VictoriaMetrics operator and single-node metrics store, vmagent, vmalert, Alertmanager and Grafana. Grafana is exposed only through the internal `grafana.krapulax.home` HTTPRoute. This HTTP endpoint assumes the home network is trusted; Grafana requires authentication and public exposure is not configured. Its admin user and password are stored in `home-dc-kubernetes/infra` in Doppler as `GRAFANA_ADMIN_USER` and `GRAFANA_ADMIN_PASSWORD`. Alertmanager syncs only `SLACK_WEBHOOK_MONITORING` into its own namespace-scoped Secret, mounts it as a file and sends resolved notifications. An isolated Alertmanager using the production receiver delivered one synthetic firing and one resolved notification to Slack without reported failures; the deployed stack still requires end-to-end validation.

Slack notifications use an explicit template instead of Alertmanager's default, which printed every shared label value as the title and omitted the annotations. The title is `[FIRING:n] alertname (cluster)`, the body lists each alert's summary and description (a resolved alert gets a check mark and "(resolved)"), the colour is yellow for warnings, red for `severity=critical` and green when resolved, and two links point at the filtered alert list and a pre-filled silence form. Labels such as `pod`, `container` and `instance` on kube-state-metrics alerts describe the scraper, not the affected workload, so they are deliberately not shown; put the workload identity in the alert's `summary`. Links need `externalURL` (`http://alertmanager.krapulax.home`); vmalert's `external.url` is Grafana, because the chart appends an Explore query to it for each alert's source link. Both settings were verified with an isolated Alertmanager and a capture webhook (firing, mixed, resolved and critical payloads) and by opening the links in the live Alertmanager and Grafana. Changing `externalURL` restarts the Alertmanager StatefulSet; silences are not persisted and would be lost.

The chart's Alertmanager component uses the short name `alerts`: its default generated StatefulSet name made the Kubernetes controller-revision label exceed 63 characters and prevented Pod creation. This override affects Alertmanager and its generated notifier/secret names only, not the VMSingle PVC. Validate the new StatefulSet, notifier target and a firing/resolved Slack test after reconciliation.

VictoriaMetrics and Alertmanager are also exposed on the internal gateway as `victoriametrics.krapulax.home` and `alertmanager.krapulax.home` (HTTP, no Cloudflare route); external-dns publishes the records from the HTTPRoutes and the Homepage "Infra Cluster - monitoring" group links to both. Neither UI has authentication, so access relies on the same trusted-LAN assumption as Grafana. The VictoriaMetrics route is an exact-path allowlist, not a prefix match: VictoriaMetrics dispatches some write routes (such as `/api/v1/import/prometheus`) without checking the HTTP method, so GET on whole API prefixes would allow writes. It allows GET only on exact read-only endpoints (the UI plus query, query_range, series, labels, label values, status, metadata) and POST only for the exact query, query_range, series and labels endpoints (VMUI POSTs long queries). Remote write, import, export, delete_series, snapshot, metrics and internal management endpoints return 404 at the gateway; verified through the gateway, including GET and POST import attempts. Add new read endpoints to the allowlist deliberately. Alertmanager is fully reachable, so any LAN client can create silences or post synthetic alerts to Slack. Add authentication before widening network access.

Homepage runs in app-cluster discovery mode, so the three infra monitoring UIs are supplied as explicit static entries by `scripts/ensure-homepage-annotations.py`, alongside the existing generated infra links such as LiteLLM. They appear under `Infra Cluster - monitoring`; VictoriaMetrics links directly to `/vmui/`. The generator continues to exclude other internal routes. Assumption: the browser can resolve and reach the `.krapulax.home` addresses on the LAN. Validate the generated `services.yaml`, rerun the generator to check idempotence, and open all three cards from a LAN browser after Argo reconciliation. Revert the Homepage change to remove the cards; monitoring routes and workloads are unaffected.

The infra Talos controller-manager binds its metrics listener to `127.0.0.1`; the chart's default Service cannot reach it and its generated name also exceeds the Service 63-character limit. Its scrape is disabled until a verified, secure collection path is designed. This is a control-plane telemetry gap, not proof that the controller is healthy.

The PVE exporter is an independently reconciled app in infra-cluster. It uses the dedicated `prometheus@pve!victoriametrics` read-only, privilege-separated `PVEAuditor` token, maintained by the Ansible role in `home-dc-proxmox`. Doppler exposes the host project's `PVE_MONITORING_TOKEN_SECRET` to the infra config by cross-project reference; the operator's service identity was verified to resolve it. The token is mounted as a file, never baked into the chart or command line. The exporter validates `10.0.40.10:8006` against the independently acquired PVE CA. A certificate-authority replacement must be verified via a trusted host connection and updated in Git before it can be trusted by the exporter. See the host repository's `docs/monitoring-credentials.md` for token provisioning, expiry, rotation and revocation.

The separately reconciled PBS exporter uses `prometheus@pbs!victoriametrics`, an audit-only token provisioned by `home-dc-terraform`'s `pbs-monitoring-apply` task. Its token is referenced into `home-dc-kubernetes/infra` from Doppler and mounted as a file. PBS uses a self-signed certificate whose SAN contains `pbs.krapulax.home`, not its IP; the exporter pins the public certificate and maps that name to `10.0.40.20`. Verify a replacement certificate over trusted PVE access before updating the pinned public certificate in Git. The exporter was tested against PBS 4.2.8 with verified TLS. The certificate and ACLs must be rotated deliberately; see `home-dc-terraform/proxmox/README.md`.

For cross-cluster ingestion, the app-cluster vmagent sends remote-write traffic to an infra-cluster TLS proxy at `10.0.40.107:8443`. The proxy accepts only `POST /api/v1/write` from a client with a certificate signed by a dedicated monitoring CA; it forwards that path to VMSingle and exposes no query or admin API. The server certificate contains the load-balancer IP as a SAN. Server and client private keys are scoped to the infra and apps Doppler configs respectively; the public CA is shared. This is a private-LAN endpoint, not public ingress. An isolated test verified that authenticated writes succeed, unauthenticated requests and non-write paths fail, and queued samples survive an agent restart and are replayed. Cluster routing and actual alert delivery remain unverified.

PVE disk and pool collection supplements the upstream exporter using the same read-only token and TLS-verified PVE API. A separate unprivileged collector reads SMART and ZFS status without SSH or privileged Pods. SMART temperature and wear data depend on what the API reports for each disk. For board and CPU sensors unavailable through that API, `home-dc-proxmox` installs Debian's unprivileged node-exporter on `10.0.40.10:9100`, restricted to mutually authenticated TLS with a dedicated CA. Its server key is scoped to `home-dc-proxmox/prd`; the infra collector's client key is scoped to `home-dc-kubernetes/infra`. The CA private key is discarded. `task monitoring:pve-hardware-pki-check` checks the identities and `task monitoring:pve-hardware-pki-create` creates them only when all are absent. The host service is already applied; its Ansible role and procedures are in `home-dc-proxmox` PR #18, stacked on credential PR #17.

PBS task monitoring uses the audit-only `/nodes/localhost/tasks` API. A separate read-only collector reports the latest completed outcome per backup/verify/prune/GC/sync task identity, a scrape-success signal and whether the bounded task-history limit was reached. Running tasks and task messages are not exported; the latter may contain sensitive details. A newer successful completion clears a prior failure. Missing schedules and jobs that never run require separate inventory/freshness checks; a task listing alone cannot prove successful backups.

PVE currently schedules guests 4090 and 4095–4097 weekly on Sunday and PBS guest 4020 monthly. Freshness alerts use nine-day and 40-day thresholds respectively, including explicit alerts for missing guest series; update those thresholds and IDs when schedules or inventory change. At inspection, the latest snapshot verification metrics for all five guests were `0`, and PBS had no configured verify jobs. The exporter uses `0` for both unverified and failed verification, so a single delayed warning says “not verified OK”; inspect PBS rather than treating `0` alone as proof of failure. Configure and independently validate verification before relying on these backups.

## Coverage and deliberate gaps

-   Live queries show four app-cluster nodes and two infra-cluster nodes, with the expected cluster labels. The app collector's authenticated remote-write path is operating.
-   Node-exporter collects Talos `/var` and the app worker local-path user volume. A separate unprivileged filesystem-only exporter mounts `/media` and `/k8s-backup` read-only; live queries show both export capacities. An inaccessible export or collector reports telemetry unavailable, not proof of a NAS failure.
-   Workload alert semantics (found during the first real incident, a sabnzbd OOM loop): a crash-looping pod is Ready for ~30 s between kills, so state-based alerts (`available < desired`, `CrashLoopBackOff`) reset and flap. `KubernetesDeploymentUnavailable` therefore uses a 15 minute average, `KubernetesPodCrashLooping` counts restarts (>3 in 30 minutes) and `KubernetesContainerOOMKilled` fires on an OOMKilled restart in the last 15 minutes. Restart growth is `max_over_time - min_over_time` of the counter, not `increase()`: VictoriaMetrics `increase()` counts a newly appeared series' first value as growth (replayed history: 9 healthy pods with constant restart counters matched), and an `offset` guard instead would hide brand-new pods, including startup OOMs, for the first 15-30 minutes. Restart counters never decrease within one pod, so max - min is exact from the pod's first sample. The crash-loop rule additionally requires the pod's series to be live (`and on (...) <counter>`): range functions keep seeing a deleted pod's samples for the whole window, so without it a replaced pod alerts for up to 30 minutes after the problem was fixed (seen live right after the sabnzbd fix). A restart that happens before the first scraped sample is not counted. There is no early warning before an OOM until cAdvisor/kubelet metrics (working set versus limit) are collected; that needs trusted kubelet serving certificates (see the kubelet gap below).
-   App-protect CronJobs are checked for stale or never-successful config exports, using the current daily schedule. This does not prove that Backrest subsequently created, checked or restored a snapshot; Backrest plan freshness and restore verification remain separate monitoring gaps.
-   The `network/krapulax-dev-production` certificate is valid for 160 hours, so a generic 14-day expiry warning would fire continuously. The initial warning instead triggers below 24 hours after 30 minutes, deduplicates replicas and uses cert-manager's `exported_namespace` label. This assumes renewal begins substantially earlier; review the threshold if the certificate duration or renewal policy changes.
-   Kubelet, cAdvisor and resource scrapes are disabled because the node-serving certificates do not chain to the cluster CA. API-server proxying is not assumed to fix this. The existing app-cluster metrics-server still has its pre-existing `--kubelet-insecure-tls` setting; this deployment does not change that workload. Its insecure ServiceMonitor is disabled and excluded from conversion. Do not add insecure VictoriaMetrics scrapes; restore these metrics only after establishing verified serving identities.
-   The community dashboard [Grafana 15661](https://grafana.com/grafana/dashboards/15661-k8s-dashboard-en-20250125/) (revision 2, 2025-01-23) is vendored at `kubernetes/apps/infra-cluster/monitoring/victoriametrics/config/dashboards/k8s-dashboard-15661.json` and provisioned from Git (no deploy-time download). It was adapted: the datasource is the provisioned `VictoriaMetrics` uid, the original `origin_prometheus` label/variable became `cluster` and a stable uid was set. Its kube-state panels (nodes, workloads, requests/limits, allocatable) work for both clusters; its CPU, memory-working-set and network panels need cAdvisor `container_*` metrics, which are not collected (see the kubelet gap above), so they show No data. Re-vendor deliberately when updating.
-   Live collectors report PVE host, VM and storage metrics, disk SMART and ZFS pool health, CPU and fan sensors, PBS availability, datastore capacity, snapshot timestamps and completed task outcomes. Complete scheduled-job coverage remains unverified.
-   The app-cluster collector converts existing Prometheus `ServiceMonitor` and `PodMonitor` resources, excluding the insecure metrics-server monitor. Its encrypted, mutually authenticated remote-write path and queue replay were tested in isolation; cert-manager, Cilium, GPU operator and node exporter targets were observed live.
-   The app controller-manager and both clusters' scheduler targets were observed down; the infra control-plane components bind to loopback. Do not interpret these missing scrapes as component failure. Establish a secure local collection path before claiming control-plane coverage.
-   QNAP telemetry is optional and not implemented. Uptime Kuma continues to own external website checks.
-   The Grafana infrastructure, PVE and PBS dashboards were opened against live metrics. Alertmanager failed to start due to the generated StatefulSet label; its naming fix and in-cluster firing/resolved Slack verification remain deployment gates. Backup restore and full end-to-end monitoring acceptance remain open.

## Dashboards and disk health

Dashboards are provisioned from Git through the Grafana sidecar. Each dashboard ConfigMap carries a `grafana_folder` annotation (`Kubernetes`, `Infrastructure`, `Backup`, `Kiosk`) and Grafana mirrors that as a folder. The community K8S dashboard (15661) was audited query by query: 68 of its 151 queries returned no data because they need cAdvisor and kubelet volume metrics, which are not collected (see the kubelet gap above). Those panels were removed; re-vendor the dashboard when a verified kubelet path exists. The Argo CD community dashboard (14584) is not provisioned: on Argo CD v3.5.6 the controller does not expose the `argocd_app_*` and `argocd_cluster_*` series it needs.

SMART data comes from two paths. The two infra nodes run a privileged `smartctl-exporter` DaemonSet (read-only SMART queries; it needs raw block-device access and the `monitoring` namespace allows privileged pods). `pve-00` uses the node-exporter textfile collectors for SMART and NVMe already installed on the host. The `Disk SMART health` dashboard combines both. App-cluster VMs have virtual disks without SMART, so their physical disks are the `pve-00` ones. The `disk-health` alert group covers SMART failure, NVMe media errors, bad sectors, wear above 80 percent, disk temperature and a missing collector; it is tested with `promtool`. The QNAP NAS has no SMART collection.

The `Homelab status (kiosk)` dashboard is meant for a wall tablet: large status tiles and two trend panels, one-minute refresh. Grafana playlists live in Grafana's own database, which is not persistent here, so create the playlist in the UI after each Grafana restart or keep using the dashboard directly.

## Storage and recovery

VictoriaMetrics uses a 20 GiB `local-path` PVC with 30-day retention. Its metric history is intentionally opted out of app-protect and can be lost with the worker; a retained local PV is not an offsite backup. Grafana has no persistent database: provisioned dashboards, datasource settings and admin credentials are reconstructed from Git and Doppler. UI-created dashboards, user accounts and other unprovisioned changes will not survive a restart. Alertmanager silence persistence is not configured; active silences can be lost on restart.

The app vmagent runs as a Deployment (not a StatefulSet) on a standalone 5 GiB Longhorn claim (`persistent-queue-data-vmagent-vmagent-app-victoria-metrics-k8s-stack-0-longhorn`, mounted by the operator as volume `persistent-queue-data`) with a 4 GiB queue limit; its transient queue is explicitly opted out of app-protect. Oldest buffered metrics are dropped if the limit is reached. The volume is replicated across the three workers but is a single failure domain with them; the old local-path claim is retained during soak. `task monitoring:remote-pki-check` checks existing Doppler identities and fails if they are incomplete or within 30 days of expiry; `task monitoring:remote-pki-create` creates them only if all are absent. The tasks require a Doppler identity able to access both the `infra` and `apps` configs. The one-year server and client certificates require planned coordinated replacement before expiry: generate and verify a new CA plus both identities, update both Doppler scopes, restart the proxy and collector, verify mTLS and queued replay, then retire the old credentials. The CA private key is discarded at initial creation, so this is a coordinated rotation, not an in-place certificate renewal. Do not rotate only one side.

## Validation and lifecycle

Render the chart with `helm template --include-crds`, render both kustomizations, and validate custom resources against the rendered CRD schemas. The chart's mutable dashboard/rule download job and Helm pre-delete cleanup hook are disabled; CRDs require an explicit reviewed lifecycle and must not be removed while other VictoriaMetrics resources use them. Validate rules with `promtool` and Alertmanager config with `amtool`. After deployment verify all scrape targets and labels, the internal Grafana route, correct dashboard data, firing and resolved Slack delivery, resource use and retention. Exercise recovery without disrupting Backrest.

Rollback is to revert the relevant Argo Applications and manifests, preserving PVCs, Doppler secrets and shared CRDs until their ownership is reviewed. Do not delete the monitoring namespace or Uptime Kuma. A complete infra-cluster, NAS or power outage can also take down this monitoring stack; an independent external dead-man alert remains separate work.
